## Current local host evidence

Environment: Linux x86_64, Node `v24.19.0`, Codex CLI `0.159.0-alpha.3`.
The installed CLI is the authoritative source for the protocol below; it was
inspected without starting a parent, changing global settings, or copying auth.

```bash
codex --version
codex app-server generate-ts --experimental --out /tmp/systemone-codex-protocol
codex app-server daemon version
```

The generated protocol provides more explicit semantics than the earlier
Desktop evidence:

- `v2/Thread.ts` exposes nullable `model` and `reasoningEffort`. Its comments
  define these as current configured values when loaded, otherwise latest
  persisted values, and explicitly say they are **not per-turn execution
  telemetry**. A `thread/read` result cannot alone establish effective execution.
- `v2/ThreadItem.ts` labels collaboration `model` and `reasoningEffort` as
  **requested** settings. `v2/CollabAgentState.ts` contains status and message.
- `v2/ModelReroutedNotification.ts` has `threadId`, `turnId`, `fromModel`,
  `toModel`, and `reason`. It is a possible model-reroute observation to retain
  in a future live run, but contains no effort and was not observed here.
  Absence of this notification would not prove the requested model ran.
- `v2/ModelVerification.ts` is the `trustedAccessForCyber` enum; despite its
  name, it does not report effective model or effort.
- `codex app-server daemon version` exited 1: the configured local app-server
  control socket does not exist. No running daemon was accessible through that
  command. No daemon was started to manufacture an observation surface.

These findings apply to the inspected cloud CLI, not an uninspected Desktop
installation. They do not prove that every possible host lacks telemetry.
